## 1. fuzzing이란
Fuzzing은 입력을 **자동으로 생성하거나 변형**해서 대상 프로그램(Target)에 넣고, Crash·Timeout·오류 조건이 나오는지 검사하는 테스트 방식이다. 입력을 만들어 던지는 프로그램이 **fuzzer**다.

### 일반 테스트와의 차이
| 관점 | 일반적인 예제 테스트 | Fuzzing |
|---|---|---|
| 입력 | 사람이 고른 사례 | 자동 생성·변형한 다수의 사례 |
| 확인 | 예상 출력과 비교 | Crash·Timeout·오류 조건 검사 |
| 장점 | 요구사항을 명확히 검증 | 사람이 놓친 경계 조건을 탐색 |
| 한계 | 사례 선택에 영향받음 | 입력과 판정 기준에 영향받음 |

### Fuzzer의 기본 동작 (4단계)
1. **입력 생성:** 새 데이터를 만들거나 Seed를 변형
2. **Target 실행:** 대상 프로그램에 입력 전달
3. **결과 판정:** 정상·거부·오류·시간 초과를 구분
4. **입력 보관:** 문제를 재현할 수 있도록 입력과 로그 저장

### 무엇을 "오류"로 볼까
fuzzer는 실행 결과를 정상 처리, 예상한 입력 거부, 메모리 오류, 비정상 종료(시그널), 시간 초과 등으로 나눈다. 포인트는 두 가지다. ① **"입력을 정상적으로 거부"한 것과 "메모리 오류"를 구분**해야 한다. ② **정상 종료했다고 안전하다는 증거는 아니다.** 그 입력에서 안 터졌을 뿐이다.

메모리 오류는 조용히 지나가는 경우가 많아서, 컴파일할 때 **AddressSanitizer(ASan)**를 켜서 범위 초과 같은 오류를 즉시 진단하게 만든다. 즉 **fuzzer는 결과를 분류하고, 메모리 오류 자체는 ASan이 탐지한다.**

## 2. Fuzzing의 분류 기준 (3가지 축)

| 기준 | 구분 | 의미 |
|---|---|---|
| 입력 생성 | Generation / Mutation | 새로 생성 / 기존 입력(Seed)을 변형 |
| 실행 정보 | Blind / Coverage-guided | 경로 피드백 미사용 / 사용 |
| 내부 정보 활용 | Black / Grey / White-box | 내부 정보를 얼마나 쓰는가 |

- **Generation:** 형식·문법을 정의해 처음부터 만든다. 구조가 엄격한 입력에 유리하다.
- **Mutation:** 올바른 Seed를 조금씩 변형한다. 구현이 간단하지만 Seed 품질에 좌우된다.
- 둘 중 하나가 낫다기보다 **실제로는 섞어서** 쓴다.
- **Blind:** 실행 경로를 보지 않고 던진다. 다음 입력 선택에 피드백을 쓰지 않는다.
- **Coverage-guided:** 어떤 코드 경로를 실행했는지 보고, **새 경로를 열어 준 입력만 남겨** 점점 깊이 들어간다. AFL++가 대표.
- **Black/Grey/White-box:** 내부를 전혀 안 보는 것 / 커버리지 같은 가벼운 정보만 쓰는 것 / 소스·심볼릭 분석 등 내부를 적극 쓰는 것.

## 3. 왜 피드백이 중요한가: Coverage-guided
입력이 `ABCD`일 때만 끝까지 들어가는 프로그램을 생각해 보자. 4바이트를 완전히 무작위로 맞추려면 평균 약 2^32(약 43억) 번을 시도해야 한다. 반면 `A`를 맞춘 입력이 "한 단계 더 깊이 들어갔다"는 신호(새 커버리지)를 주면 그 입력을 **보존하고 거기서 다음 바이트를 변형**하므로, 바이트별로 차례차례 맞춰 나갈 수 있다.

AFL++는 이 아이디어를 컴파일러 계측(coverage instrumentation)으로 실제 프로그램에 적용한 도구다. 기본 사용 형태는 다음과 같다.
```bash
afl-clang-fast -fsanitize=address -g -o target target.c   # 커버리지 계측 + ASan 빌드
mkdir in && echo "hello" > in/seed
afl-fuzz -i in -o out -- ./target                          # 크래시 입력은 out/ 에 저장
```

## 4. 대표 fuzzer 정리
| 도구 | 특징 | 주 용도 |
|---|---|---|
| **AFL++** | 커버리지 기반 grey-box, 계측 빌드 | C/C++ 바이너리, 파일/표준입력 |
| **libFuzzer** | LLVM 내장, 함수 단위 인프로세스 | 라이브러리 함수 (하네스 작성 필요) |
| **Honggfuzz** | 커버리지 기반, 멀티프로세스 | C/C++ 등 |
| **syzkaller** | 시스템콜 문법 기반 | 리눅스 커널 |
| **boofuzz** | 프로토콜 정의 기반 | 네트워크 서비스 |
| **OSS-Fuzz** | fuzzer가 아니라 **지속적 fuzzing 인프라** | 오픈소스 프로젝트 |

선택 기준: 소스와 함수 단위가 분명하면 libFuzzer 하네스, 실행 파일 단위로 빠르게 시작하려면 AFL++, 커널은 syzkaller, 소스 없는 네트워크 서비스는 boofuzz 같은 프로토콜 기반이 어울린다.

## 5. 장단점 한눈에 보기
| 장점 | 단점 |
|---|---|
| 사람이 떠올리지 못한 경계 입력을 대량으로 시험한다 | 깊은 조건, 논리 버그에는 약하다 |
| 한 번 세팅하면 자동으로 오래 돌릴 수 있다 | 하네스·Seed 준비에 시간이 들고, 결과 분류(triage)가 필요하다 |
| 크래시 입력이 남아 재현과 수정 검증이 쉽다 | 크래시가 곧 취약점은 아니다 (영향 분석 필요) |

## 6. 한계와 버그 바운티와의 연결
- 체크섬·매직 넘버·복잡한 상태 같은 **깊은 조건**은 못 넘는 경우가 많다. Seed와 사전(dictionary), 하네스 설계가 성패를 가른다.
- 크래시가 모두 **악용 가능한 취약점**은 아니다. 분류와 영향 분석이 필요하다.
- 인증 우회 같은 **논리 취약점**은 크래시로 드러나지 않아 못 잡는다.
- 흐름: 오픈소스에서 fuzzing → 크래시 입력 보관 → 재현 → 원인 분석(ASan 로그) → 보안 영향 판단 → 제보. 버그 바운티의 대표적인 한 줄기다.

### 7-2. 실습 1: Blind Fuzzing

#### 구조
`tools/fuzz.py`가 아래 일을 한다.
1. 난수 Seed(`--rng-seed`)로 **입력을 재현 가능하게** 만든다. 같은 Seed면 같은 입력 순서가 나온다.
2. 0~64바이트 길이, 0~255 값의 **무작위 바이트**를 만든다. 버퍼가 16바이트이므로 16바이트보다 긴 입력도 일부러 섞이게 하는 것이다.
3. 입력을 임시 파일로 저장해 Target을 실행하고, 시간 제한(timeout)을 둔다.
4. stderr에 `ERROR: AddressSanitizer:`가 있으면 `sanitizer`, 시그널 종료는 `signal`, 종료 코드 0은 `accepted`, 2는 `rejected`로 분류한다. ASan 메시지를 **먼저** 보는 이유는, 종료 코드만으로는 메모리 오류가 가려질 수 있기 때문이다.
5. 처음 문제가 생긴 입력(`first_finding.bin`)과 오류 메시지를 저장한다. **입력을 보관해야 fuzzer 없이도 다시 실행해 원인을 분석**할 수 있다.

#### 실행
```bash
cd fuzzing-lab/mission1_buffer_boundary && make
python3 tools/fuzz.py --mode blind --target ./build/target_easy \
  --runs 100 --rng-seed 7 --out results/blind_easy
cat results/blind_easy/report.json
./build/target_easy results/blind_easy/first_finding.bin     # 재현
```

#### 결과
수업 자료에 제시된 제작 환경의 관찰 결과는 다음과 같다.

| 측정 항목 | 수업 자료의 관찰값 |
|---|---|
| 테스트 횟수 | 100 |
| 정상 처리(accepted) | 22 |
| 정상적인 거부(rejected) | 0 |
| ASan 메모리 오류(sanitizer) | 78 |
| 첫 오류 입력 | 1번째 테스트 / 41바이트 |

입력 길이를 0~64(65가지)에서 균등하게 뽑으면 16바이트 이하일 확률은 17/65, 약 26%다. accepted 22건은 이와 대략 맞는다. (Target이 끝에 널 문자를 붙인다면 경계가 1바이트 당겨질 수 있으니 아래 미션 1에서 실제 경계를 확인한다.)

- **Q2. ASan이 탐지한 오류 종류는? READ인가 WRITE인가?**

`target_easy_fixed`처럼 복사 전에 16바이트 경계를 검사하게 고치면, 같은 입력에서 오류가 사라지는지 **재검증**한다. 입력을 저장해 둔 덕분에 같은 입력으로 다시 확인할 수 있다.

### 7-3. 실습 2: Coverage-guided fuzzer 직접 만들기
수업의 두 번째 실습은 **새로운 실행 경로를 연 입력만 Queue에 저장하는 fuzzer**를 직접 만드는 것이었다. 조건: 시작 Seed는 `AAAA`, Queue에서 입력 하나를 골라 `mutate()`로 변형하고, `target()`으로 커버리지를 확인해 **새 커버리지를 발견하면 Queue에 저장**하며, 모든 조건을 통과하는 `ABCD`를 찾으면 종료한다. 3장에서 본 아이디어를 그대로 코드로 옮긴 것이다.

아래는 개념을 확인하려고 내가 정리한 최소 구현이다.
```python
import random

def target(data: bytes):
    """ABCD를 앞에서부터 맞출수록 더 깊이 들어가는 대상. (커버리지 집합, 성공 여부)"""
    cov = set()
    if len(data) != 4:
        return cov, False
    cov.add("len4")
    for i, ch in enumerate(b"ABCD"):
        if data[i] != ch:
            return cov, False
        cov.add(f"byte{i}")
    return cov, True

def mutate(data: bytes, rng):
    b = bytearray(data)
    b[rng.randrange(len(b))] = rng.randrange(256)   # 한 바이트만 바꾼다
    return bytes(b)

def coverage_guided(seed=b"AAAA", rng_seed=1):
    rng = random.Random(rng_seed)
    queue, seen = [seed], target(seed)[0]
    n = 0
    while True:
        n += 1
        cand = mutate(rng.choice(queue), rng)
        cov, ok = target(cand)
        if ok:
            return n, cand
        if not cov <= seen:        # 새 경로를 열었으면 Queue에 보관
            seen |= cov
            queue.append(cand)
```
난수 Seed를 1~20으로 바꿔 20번 돌려 보니 `ABCD`를 찾기까지 1,409~16,766번(중앙값 약 5,200번)이 걸렸다. 같은 대상에 무작위 4바이트를 100만 번 던져서는 찾지 못했다(기대값은 약 43억 번). **피드백 하나가 탐색 비용을 몇 자릿수 줄인다**는 것을 보여 준다. (직접 돌린 환경에서의 관찰이며, 정확한 횟수는 난수 Seed에 따라 달라진다.)

> ✏️ AFL++ 실행 화면(실행 속도, 경로 수, crashes 개수)은 **추후 보완 예정**입니다.
{: .prompt-info }

### 7-4. 같은 아이디어를 AI에도: Prompt Mutation
수업 후반에는 프롬프트 인젝션(PI)을 다뤘는데, 구조가 fuzzing과 똑같아서 인상 깊었다.
- **Seed:** 기본 공격 프롬프트 하나
- **Mutation:** 역할(Role Playing), 접두사/접미사, 표현을 조금씩 바꿈
- **Feedback:** AI가 원래 지시를 지켰는지 결과를 기록

같은 입력도 AI는 결과가 달라질 수 있으므로 **여러 번 시험해 변동을 보고, 한 번의 성공보다 재현 가능한 결과**를 봐야 한다는 점도 fuzzing의 "문제 입력 보관·재현"과 닮았다. (내가 관심 있는 AI 에이전트 보안과 이어지는 지점이라 따로 더 공부해 볼 예정이다.)
